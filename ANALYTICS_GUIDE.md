# Руководство по аналитике и мониторингу HabitTracker

В этом документе описано, как использовать внедренную систему аналитики, мониторинга производительности и сбора ошибок.

## 🛠 Используемые инструменты

*   **Firebase Analytics**: Бизнес-метрики и поведение пользователей.
*   **Firebase Crashlytics**: Отчеты о вылетах и некритичных ошибках.
*   **Firebase Performance**: Мониторинг быстродействия (запуск, сеть, экраны).
*   **Timber**: Интеллектуальное логирование (Console в Debug, Crashlytics в Release).

## 📊 Где смотреть данные

Все данные доступны в [Firebase Console](https://console.firebase.google.com/):

1.  **Вылеты и ошибки**: Раздел `Release Monitor` -> `Crashlytics`.
2.  **Поведение пользователей**: Раздел `Analytics` -> `Dashboard` или `Events`.
3.  **Скорость работы**: Раздел `Release Monitor` -> `Performance`.
4.  **Отладка в реальном времени**: Раздел `Analytics` -> `DebugView` (позволяет видеть события прямо сейчас при разработке).

## 🚨 Кейс: У пользователя стабильный вылет через 30 секунд

Если вы получили жалобу на стабильный вылет, следуйте этой инструкции:

### Шаг 1: Поиск ошибки в Crashlytics

1.  Зайдите в раздел **Crashlytics**.
2.  Убедитесь, что фильтр версии соответствует версии приложения пользователя (например, `1.3.5`).
3.  Вы увидите список "Issues". Самые частые вылеты будут в топе.
4.  Нажмите на проблему. Вы увидите **Stack Trace** — он покажет точную строку кода, где произошел сбой.

### Шаг 2: Анализ контекста (Logs & Keys)
Crashlytics сохраняет не только ошибку, но и путь пользователя:
*   **Logs**: Вкладка "Logs" покажет последние действия пользователя перед вылетом (например, `Tag: HabitsViewModel, Message: Loading habits for...`). Благодаря Timber, все важные логи попадают сюда.
*   **Keys**: Вкладка "Keys" может содержать кастомные данные, которые мы установили (например, `habit_id`).
*   **User ID**: В строке поиска или в деталях ошибки вы увидите ID пользователя, если он был авторизован. Это позволит вам найти его данные в Firestore для воспроизведения бага.

### Шаг 3: Анализ цепочки событий (Analytics)

Если Stack Trace не дает полной картины:

1.  Скопируйте `User ID` из Crashlytics.
2.  Перейдите в **Analytics** -> **User Explorer**.
3.  Найдите этого пользователя. Вы увидите хронологию его действий:
    *   `screen_view` (какие экраны открывал).
    *   `habit_completed` (что нажимал).
    *   `app_exception` (момент вылета).
Это поможет понять, какая последовательность действий приводит к проблеме.

## 📈 Основные события (Events)

| Событие | Описание | Параметры |
| :--- | :--- | :--- |
| `habit_created` | Создание новой привычки | `habit_id`, `habit_type` |
| `habit_completed` | Отметка о выполнении | `habit_id` |
| `login` / `sign_up` | Авторизация пользователя | `method` (например, google) |
| `challenge_joined` | Вступление в челлендж | `challenge_id` |
| `screen_view` | Переход на экран | `firebase_screen`, `firebase_screen_class` |

## 💡 Советы по разработке

*   **Логирование**: Используйте `Timber.e(t, "message")` для ошибок. В релизе это автоматически создаст "Non-fatal" отчет в Crashlytics.
*   **DebugView**: Чтобы видеть события в реальном времени при разработке, выполните команду в терминале:
    `adb shell setprop debug.firebase.analytics.app com.habittracker`
*   **Performance**: Если экран открывается медленно, Firebase Performance автоматически пометит его как "Slow rendering" в консоли.
